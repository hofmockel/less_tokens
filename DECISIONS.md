## Accepted

Reopen this window only with a release-tagged schema plus live Bash/apply_patch probes on a newly claimed release.

- **PC1 — Both platforms expose real cache counters; not a platform limitation** *(telemetry / cost and rate-limit efficiency)* — Verified against live transcripts, not inferred from size. Claude Code: every assistant-turn `usage` object in `~/.claude/projects/<slug>/*.jsonl` carries `input_tokens` (fresh-only), `cache_creation_input_tokens`, `cache_read_input_tokens`, and a nested `cache_creation.{ephemeral_5m_input_tokens, ephemeral_1h_input_tokens}` breakdown; observed stable across CLI 2.1.181–2.1.215. Codex CLI: `event_msg` lines with `payload.type == "token_count"` carry `info.total_token_usage.{input_tokens, cached_input_tokens, output_tokens, reasoning_output_tokens, total_tokens}` in `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`; `cached_input_tokens` is present across the whole 0.142.3–0.145.0-alpha.18 observed range (covers CX26's verified 0.142.3–0.144.6 window), but `cache_write_input_tokens` is a new field that only appears from 0.145.0-alpha.18 onward — absent, not zero, on every verified-window release. Critical schema divergence: Codex's `input_tokens` is a *total* (`input_tokens = total_tokens − output_tokens`, includes cached), while Claude's `input_tokens` excludes cache entirely — a shared cache-read-share formula across platforms would silently double-count. Each platform needs its own formula: Claude `cache_read_input_tokens / (input_tokens + cache_creation_input_tokens + cache_read_input_tokens)`; Codex `cached_input_tokens / input_tokens`. **Verdict:** not a platform limitation — both expose genuine native counters, so PC1 graduated from Research to Ready in `BACKLOG.md` and has since shipped (`agents/common/cache_health.py`, wired into `stats.py`'s reports). Transcript discovery: Claude is deterministic — the hook payload's native `session_id` *is* the transcript filename stem (verified: a transcript line's own `sessionId` matches it exactly), so `~/.claude/projects/<slugify(cwd)>/<session_id>.jsonl` needs no search; falls back to newest-mtime in the slug directory when no payload-sourced id is available. Codex, as expected, isn't cwd-organized — resolved via a `cwd`-field grep across recent `rollout-*.jsonl` files, skipping nested subagent rollouts (`thread_source == "subagent"`), verified end-to-end against a live 69-turn transcript (91.9% average cache-read share). Abrupt-miss-window rule: a cache-read share dropping ≥30 points off a ≥70%-warm trailing 5-turn baseline — an initial estimate, not yet calibrated against a real miss event (no calibration corpus exists; tracked under D4's benchmark work). Reopen only if a future transcript sample contradicts a field name or semantics above, once CX32 widens the Codex verified window past 0.144.6 (cache-write reporting would then need re-verifying against whatever the new anchor's schema shows), or once real abrupt-miss data suggests the 30pt/70%/5-turn constants need adjusting.

- **HS1 — Fuse SQLite FTS5/BM25 lexical retrieval into vector search via RRF** *(input / retrieval)* — `_search_sqlite()` ranked purely by dense-vector cosine similarity; HS1 benchmarked vector-only vs lexical-only vs RRF-fused retrieval on a versioned 14-query held-out set (7 semantic + 7 exact, exact ground truth computed automatically) across two real indexed repos (`less_tokens`, 416 chunks; `ever_better`, 6,115 chunks). The original hypothesis (lexical rescues exact identifiers) did not hold — vector-only already hit recall@5=MRR=1.0 on exact queries in both corpora. The real, unexpected win: fusion rescued **semantic** queries vector-only missed via partial lexical term overlap, with zero regression on any metric in either repo — `ever_better` recall@5 0.857→1.00, MRR 0.834→0.860, mean chars-to-find (token proxy) down 82% (3656.9→634.8); `less_tokens` MRR 0.693→0.725 with recall already at ceiling. Latency cost +1-5ms (embedding call already dominates); FTS5 storage overhead 3-9% of existing vector-blob size; index build sub-30ms even at 6,115 chunks. **Verdict:** ship the fused path — every fused metric was ≥ its vector-only counterpart across both query types and both repos, at negligible cost. This research spike stops short of production integration (schema/trigger wiring, `search.py` ranking path, migration across already-installed downstream repos) — that is separate, higher-blast-radius engineering tracked as **HS2**. Full methodology, query fixtures, and raw results: `reports/runs/2026-07-22-hs1-hybrid-retrieval-benchmark/`. Reopen only if HS2's production benchmark (real installed corpora, not this spike's fixtures) disagrees.

## Rejected

- **CP1 — Snapshot-guided `/compact` nudge did not show measured recall improvement over the generic message** *(input / compaction quality)* — `compact-trigger.py`'s Claude-side hook emits a generic nudge ("Run /compact or start a fresh Claude session") while the budget control plane separately tracks per-session state (`active_files`, `decisions_made`, `test_status`, `open_questions`, `next_step`, `current_objective`) and can render it into a token-budgeted `compact_summary` via `build_compaction_snapshot()` — the two paths were never connected. Live `/compact` recall can't be scripted, so the proxy test used a fresh `general-purpose` subagent performing an analogous compaction task on a fabricated multi-thread transcript, once under a generic instruction and once under an instruction listing the real `build_compaction_snapshot()`-derived facts to preserve, scored against a fixed 8-item critical-fact checklist. Two rounds run (a single coherent thread, then a second unrelated thread appended afterward to deliberately induce recency bias against the first thread's facts) — **both conditions scored 8/8 in both rounds**, including the recency-bias round, where the generic condition still surfaced the buried thread's `next_step` unprompted. **Verdict:** per CP1's own acceptance criteria (wire only if recall measurably improves), do not wire the snapshot into the live nudge — leave `.claude/hooks/compact-trigger.py`'s message as-is. Codex side needs no action; CX20 already established hooks are advisory-only there. The fixture tested is roughly three orders of magnitude smaller than the real ~625,000–750,000-char trigger threshold (`MAX_SESSION_CHARS`) and used n=1 per condition per round, so this is "no gap detected at feasible spike scale," not proof of equivalence at real compaction scale. Full methodology, fixture, and raw outputs: `reports/runs/2026-07-22-cp1-compaction-recall-eval/report.md`. Reopen only with a realistic-scale fixture (captured from an actual near-threshold session or fabricated at that size) and enough trials to be more than anecdotal.

  1. **The installed `.codex/hooks.json` failed to parse under the CLI during the test.** The then-current flat schema (`{"hooks": [{"event","matcher","command"}, ...]}`) was rejected with `invalid type: map, expected a sequence`.   **Verdict:** the sentinel (`SENTINEL_G0URQ1VW7DPH`, planted at line 50, inside the omission window) was fully recoverable verbatim from the model's next turn — truncation did not reach the model in this configuration. `parity.json`'s `truncate-output.codex: "shipped"` is not currently substantiated by live replacement evidence. The file's vocabulary is binary (`shipped`/`missing`) today and neither fits cleanly (`missing` overstates — the code and wiring exist), so the label was not guessed at.
