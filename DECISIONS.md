# Decisions

Settled calls — accepted or rejected — recorded so they aren't re-proposed or re-litigated
without new evidence. Distinct from [BACKLOG.md](BACKLOG.md) (open work, not yet started) and
[CHANGELOG.md](CHANGELOG.md) (work already shipped). An item lands here once a verdict is
reached, whether or not any code changed.

Each entry: **what was proposed**, **the verdict**, **why**, and **what would reopen it**.

---

## Accepted

- **CX20 — Codex can initiate compaction through the experimental app-server, but hooks remain advisory** *(input / platform gap)* — Codex 0.144.6's generated v2 protocol exposes `thread/compact/start`. A bounded live probe used one synthetic thread in an empty temporary directory, received an empty success response plus a completed `contextCompaction` item, and measured context falling from 19,533 to 6,588 tokens. The rollout JSONL grew from 71,514 to 82,722 bytes because it is append-only, so file-size shrinkage is rejected as a savings measure. **Verdict:** app-server clients have real compaction control; installed less-tokens hooks do not, because their documented payload/output contract exposes neither an app-server client channel nor before/after token counts. Keep the hook nudge, claim savings only from numeric protocol/rollout token events, and re-probe this experimental method on every supported release. Reopen automatic hook initiation only when Codex exposes a stable hook-safe control channel.

- **CX29 — Use native Codex lifecycle boundaries on the verified release** *(output / context lifecycle)* — The official 0.144.6 hook contract and sanitized live fixtures expose `Stop`, `SubagentStart`, `SubagentStop`, `PreCompact`, and `PostCompact` with event-specific fields. **Verdict:** wire those events directly and remove the former wildcard `PostToolUse` substitutes. Stop checks read `last_assistant_message` and honor `stop_hook_active`; SubagentStart adds only bounded developer context; PreCompact refreshes the existing task-state snapshot; PostCompact pairs the real transcript sizes and records only measured reductions. Lifecycle outputs use the documented JSON or exit-2 continuation forms, and compaction hooks always fail open. The broader 0.142.3–0.144.6 tool-hook window remains supported, but native lifecycle delivery is claimed only for 0.144.6; earlier releases are explicitly best-effort until release-matched live evidence exists.

- **CX26 — Use one published event-keyed Codex hook contract across a bounded release window** *(correctness / platform compatibility)* — The supported window is `codex-cli 0.142.3–0.144.6`. Official release-tagged generated schemas exist at both tested anchors, and live headless probes proved the published inline event structure on `0.142.3` and `0.144.5`; after migrating this repo's actual `.codex/hooks.json`, both releases blocked an unsearched `cat README.md` through `PreToolUse:Bash`, and release-labeled `apply_patch` probes captured the non-Bash local-function payload. The installer now renders only `{"hooks":{"PreToolUse":[...]}}`, accepts the retired CX21 matcher-array representation only for upgrade/uninstall, preserves unrelated valid metadata, and fails before writes on malformed/pre-CX21-flat files or detected versions outside the verified window. Install checks verify the canonical hooks feature flag but do not claim trust or enforcement: hook trust is definition-hash scoped and must be reviewed through `/hooks`. Claims are limited to headless `codex exec`; interactive CLI, desktop UI/app-server, IDE, hosted, and specialized paths remain unverified. This supersedes CX21/CX23's matcher-array schema conclusions, which remain historical evidence for the old representation. Reopen the window only with release-tagged schemas plus live Bash and non-Bash probes on every newly claimed endpoint.

- **Subagent support is explicit, platform-specific, and evidence-gated** *(delegation / context control)* — `less_tokens` will not spawn subagents automatically or claim hook parity where the host exposes no hookable boundary. Claude's `Task` surface supports two shipped controls: SA1 replaces oversized child returns with a measured bounded digest, and SA2 records prompt/return fan-out cost without counting it as savings. Codex support remains installed pointer-first delegation guidance because no equivalent `Task` boundary is available; user authorization is required before spawning. Downstream work is conditional rather than a promised sequence: SA3 requires material prompt-side waste, SA4 requires distinct child session IDs plus concurrency evidence, SA5 requires a measurable per-role advantage over the generic cap, and SA6 requires a future harness that replays full child transcripts. Reopen the platform split if Codex exposes an equivalent spawn/return hook, and promote any roadmap item only when its `BACKLOG.md` evidence gate is satisfied.

- **CX21 — Follow the Codex CLI's nested matcher-group hook schema** *(tool / enforcement parity)* — The installer previously treated `.codex/hooks.json` as a flat list of `{event, matcher, command}` objects. Live `codex-cli 0.142.3` parsing rejected that representation before any hook could run. The accepted contract is `{"hooks":[[{"event","matcher","hooks":[{"type":"command","command"}]}]]}`: an outer list of matcher groups, with each matcher containing a typed command-hook list. Commit `7559f3b` changed `wire_codex_hooks_json` and `unwire_codex_hooks_json` to normalize valid nested groups internally, emit the CLI-compatible structure, preserve unrelated valid nested entries, and rebuild legacy flat files that the CLI rejects wholesale. Integration tests pin new-file creation, idempotency, legacy migration, and uninstall preservation. **Boundary:** this resolves configuration parsing, not CX17's separate questions about whether `codex exec` fires `PostToolUse` or whether hook stdout replaces tool output. The docs-sync audit also found that `install.py --check --agent codex` and `codex_parity_audit.py` still read the retired flat form; CX22 tracks that false-health follow-up. Revisit the schema only with a versioned CLI contract or a new live parser failure.

## Rejected

- **CX28 — Codex 0.144.6 has no model-visible tool-result replacement contract** *(tool output / enforcement proof)* — The release-matched Codex manual documents `PostToolUse` output as feedback/additional context. It accepts `systemMessage`, `continue: false`, and `stopReason`; `suppressOutput` is parsed but explicitly unsupported, and no `updatedToolOutput`/`updatedMCPToolOutput` equivalent is exposed. Live 0.144.6 fixtures prove that `PostToolUse` now fires and supplies `tool_response`, but those input fixtures do not establish replacement. The prior adapter's plain stdout plus exit 2 therefore cannot be counted as removed model-visible bytes, and its smoke test proved only local string formatting. **Verdict:** Codex truncation is marked missing and unwired; the Claude native replacement remains shipped. Known noisy Codex commands continue through CX27's pre-execution deny/rewrite controls. Revisit only when a release-matched public contract exposes result replacement/suppression, then require Bash and MCP/local-function sentinel tests before enabling telemetry. A nested live SaaS probe was not run because execution approval was denied on workspace-context disclosure grounds; no unsupported claim is inferred from that absence.

- **CX17 — Codex tool-output replacement remains unverified in `codex exec` after the schema repair** *(tool / enforcement parity)* — Tested live against `codex-cli 0.142.3` (`codex exec`) with a 5,908-char oversized `cat` output containing a random sentinel planted inside the range `truncate_bash()`'s head=30/tail=20 policy should elide. Two stacked problems were found before the original mechanism question could be reached:
  1. **The installed `.codex/hooks.json` failed to parse under the CLI during the test.** The then-current flat schema (`{"hooks": [{"event","matcher","command"}, ...]}`) was rejected with `invalid type: map, expected a sequence`. Iteratively reading serde error messages (`expected struct MatcherGroup`, etc.) recovered the CLI's real expected shape: `{"hooks": [[{"event","matcher","hooks":[{"type":"command","command"}]}, ...]]}`. At test time that disabled all 20 dogfooded Codex hooks. **Resolved 2026-07-17:** CX21 shipped the nested writer and legacy-file migration in commit `7559f3b`; configuration parsing is no longer the standing blocker. Validator parity is tracked separately as CX22.
  2. **Even after hand-correcting the schema and forcing `--dangerously-bypass-hook-trust`, `truncate-output.py`'s `PostToolUse:Bash` hook still never executed.** `savings.jsonl` gained zero new entries across three live runs; a wildcard `PostToolUse:.*` debug tap captured **zero** payloads during a `cat` tool call in the same run where an equivalent `PreToolUse:.*` tap cleanly captured one (`hook_event_name: "PreToolUse", tool_name: "Bash"`). This points at `codex exec` (headless/automation mode) not invoking `PostToolUse` hooks at all — distinct from the schema bug — but wasn't isolated against interactive `codex` TUI sessions (not scriptable for an unattended live test). `savings.jsonl`'s own pre-existing entries (dated the day before this test) show truncation events *were* logged historically, so `PostToolUse` hooks worked at some past point; whether that required interactive mode or predates the schema drift is unresolved.
  3. **CX17's original mechanism question — does Codex's `PostToolUse` stdout actually replace what the model sees, the way `updatedToolOutput` does for Claude — was never reached.** No live `PostToolUse` invocation occurred in any successful test run, so there's nothing yet to confirm or refute about the replacement contract itself. Given the shipped Claude-side fix history (`truncate-output.py` originally exit-2'd with stdout on Claude too, and was proven *not* to replace the tool result — Claude's `PostToolUse` only surfaces stderr; the real fix needed `hookSpecificOutput.updatedToolOutput`), the strong prior is that Codex's plain stdout+exit-2 contract is equally inert *whenever* the hook does fire — but that stays unverified pending points 1–2.

  **Verdict:** the sentinel (`SENTINEL_G0URQ1VW7DPH`, planted at line 50, inside the omission window) was fully recoverable verbatim from the model's next turn — truncation did not reach the model in this configuration. `parity.json`'s `truncate-output.codex: "shipped"` is not currently substantiated by live replacement evidence. The file's vocabulary is binary (`shipped`/`missing`) today and neither fits cleanly (`missing` overstates — the code and wiring exist), so the label was not guessed at. CX21 has removed the schema precondition; reopen CX17 when a valid nested install can be tested in interactive Codex and `codex exec` so `PostToolUse` firing and replacement semantics can be isolated.

- **CX18 — Codex's `Stop` hook is schema-defined but does not fire in `codex exec` headless mode** *(output / enforcement parity)* — `hook_manifest.py:181-190` assumed "Codex has no native Stop equivalent" and substituted `PostToolUse .*` for `terse-output`/`savings-html`'s Claude-side `Stop`/`SubagentStop` wiring. Live investigation against the same `codex-cli 0.142.3` used for CX17 disproves the "no equivalent" half and confirms the "doesn't fire" half:
  1. Reverse-engineering the CLI's embedded JSON Schema (`codex_app_server_protocol`, extracted from the vendored native binary at the npm package's `node_modules/@openai/codex-darwin-arm64/vendor/aarch64-apple-darwin/bin/codex`) found a complete `Stop` hook contract — `hook_event_name: "Stop"`, `last_assistant_message`, `stop_hook_active` — structurally identical to Claude's `Stop` payload and exactly the field shape `terse-reminder.py:30` was already (wrongly) trying to read as `response`. `SessionStart`, `SubagentStart`, `SubagentStop`, `UserPromptSubmit`, `PreCompact`, `PostCompact`, and `PermissionRequest` schemas exist alongside it.
  2. A scratch `codex exec` install with a bare `Stop` hook (sole entry, own matcher group) accepted the config with no parse error but never invoked the hook across a clean tool-free single-turn run — parallels CX17's `PostToolUse` finding: schema-defined, CLI-accepted, silent no-op in headless `exec` mode.
  3. A second test putting a `Stop` (`matcher: ""`) entry and a `PreToolUse` (`matcher: ".*"`) entry inside **one** matcher-group array — the exact shape `codex_hooks_json_value()` (CX21) always produces for every real install, since it packs all hook entries into a single inner list regardless of declared event — found the `Stop`-labeled script invoked anyway, carrying a `PreToolUse` payload, when only a `PreToolUse` trigger fired. That's not evidence `Stop` fires; it looks like an empty matcher acting as a group-wide wildcard independent of the declared `event` field. Filed separately as **CX23** since it's a distinct, more urgent correctness question about hooks already shipped in production, not part of CX18's own scope.

  **Verdict:** implementation is not viable yet. Wiring `terse-reminder.py`/`savings-html.py` to a real `Stop` event needs the hook to actually fire in at least one Codex invocation mode, and headless `codex exec` doesn't do that despite accepting the schema. Interactive `codex` TUI sessions remain untested (same gap CX17 left open — not scriptable for an unattended live test). Revisit alongside CX17's reopening once an interactive-session test is feasible; the schema work here means both can likely be tested together next time.

- **F3 — Terse hook block messages** *(output)* — block/reminder messages are output tokens, but paid only **on trigger**, not every turn; already trimmed once. Short learned codes (`S9: slice 51-3`) save bytes but need a legend (new fixed cost) and hurt readability. Marginal — only worth it for a hook that fires constantly. Skip. Reopen only if a hook starts firing on most turns and the block-message tokens become a measurable share of output.

- **F4 — Consolidate overlapping tools** *(meta)* — `search.py`/`search_config.py`/`symbols.py`/`parse.py` have distinct jobs (search runtime / config / symbol index / AST parse). Merging is pure refactor: zero token saving, real regression risk across both agents. Not worth it.

- **G10 — Bound subagent search breadth** *(input)* — the harness Explore agent already exposes a breadth knob (medium / very thorough); less_tokens adds nothing and cannot hook-enforce a sub-process's search scope. Owned by the harness, not this toolkit. Skip. **Dual scope:** Explore's breadth knob is a Claude harness feature. Codex has `agent_type="explorer"` but no repo-owned breadth knob; narrowness must come from the delegated prompt ("answer only X, inspect only paths matching Y"). Skip hook/config work for both — distinct reasons, recorded so neither agent re-proposes it.

- **S6 — Tiered effort** *(output)* — route tasks to Haiku/Sonnet/Opus via a tier matrix + flag. No hook can force a per-turn model downshift, so enforcement is weak and the claimed 50–70% saving is unverified. The shipped caveman Stop hook already captures output-token savings deterministically. Skip. Referenced in [DOCUMENTATION.md](DOCUMENTATION.md) → *Token-reduction strategy* (shipped-strategy table, S8–S13).

- **Graphify integration** *(input)* — evaluated 2026-07-04 (`tect`-reviewed effectiveness audit). Graphify's structural (AST) extraction is free, but its semantic extraction — the part that actually builds the knowledge graph — dispatches parallel Claude subagents that spend real input/output tokens unless a Gemini/Google API key is configured. Adopting the default build path means spending tokens to build the thing meant to save tokens: a direct inversion of this repo's mission, same reasoning already applied to reject the query/result cache (this file's neighbor ruling below — "saves embedding compute, not tokens"). The capability gap (cross-entity relationship queries, community/"god node" detection) is real but is a navigation feature, not a token-reduction lever, so it's out of scope for this repo's mission as specified. No artifact/state collision either way (`graphify-out/` doesn't touch `.claude/state/` or `.less_tokens/`) — the rejection is entirely economic. Skip. Reopen only if graphify ships a Gemini-only build mode this repo can hard-gate to, and only as an optional add-on for *host* repos this toolkit installs into, never for this repo's own dogfooding.

- **Same-session `search.py` repeated-query cache** *(input)* — reopened 2026-07-04 pending real repeat-rate evidence; resolved 2026-07-07. Real instrumentation for this shipped 2026-07-05 (`2f38b8b`, "Add near-miss instrumentation to search.py's repeated-query path"): `_record_search_near_miss()` in `.claude/tools/search.py` appends a `kind: "search"` record to `near_misses.jsonl` whenever a query exactly repeats an earlier query in the same session, fail-open and additive-only. Two lines of evidence converge: (1) after ~2 days live, the accumulated `near_misses.jsonl` shows **zero** genuine same-session repeats — its only 3 `"search"`-kind entries are pytest-fixture noise (`test_agent_model.py`/`test_bug18_mixed_model_results.py`, literal query `"anything"`, `session_id: "local-session"`); (2) independently mining the longer-window `search-history.log` (457 rows since 2026-06-06 in the actively-dogfooded `../less_tokens` client repo, 374 of which are the same pytest-literal noise — `"anything"` ×302, `"q"` ×72) leaves 83 real queries, of which only 6 repeated at all and only 3 landed within a plausible same-session window (23 sec–7 min apart); the other 3 pairs were 72 min–14 days apart, outside what a same-session cache would catch. Real same-session repeat rate ≈ 3–4% of queries. Per the item's own exit criteria, this stays periphery. Skip. Reopen only with fresh `near_misses.jsonl` evidence showing a materially higher repeat rate once more real usage accumulates — 2 days is a thin window on its own, and this verdict leans partly on the older `search-history.log` proxy rather than waiting for a longer live-instrumentation run. Full "query/result cache" framing and the embedding-cache distinction: [DOCUMENTATION.md](DOCUMENTATION.md) → *Token-reduction strategy*.
